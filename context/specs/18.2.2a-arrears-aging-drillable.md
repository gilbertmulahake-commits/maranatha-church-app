# Unit 18.2.2a: Arrears Aging — Drillable Report

## Goal
Add a read-only report at `/dashboard/reports/arrears-aging` that lists each church with its unpaid balance decomposed into 0-30 / 31-60 / 61-90 / 90+ day aging buckets, per contribution bucket (Annual / Monthly), so the National Treasurer and Regional Chairman can identify exactly which churches sit in which overdue window. No schema change; no new page files — one new slug on the existing `[report]` route. Scope of "drillable" in this unit is explicitly **church-level** — the drill into underlying periods for a single church is a documented follow-up, not silently bundled here.

## Design

### Placement and navigation
- New slug `arrears-aging` registered in `lib/utils/report-registry.ts` under the **Analytics** group, immediately after `arrears`.
- Title: **"Arrears Aging — Drillable"**. Description: **"Per-church gross arrears aged by 0-30 / 31-60 / 61-90 / 90+ day buckets (FIFO), with church-level approved write-offs disclosed separately."**
- Appears automatically in the Reports hub grid and `<ReportSelector>` via the three registry consumers — no other navigation changes.
- Build page count stays **28/28** (one new slug on the existing `[report]` dynamic route).

### Scoping decision (follows 18.1 / 18.2 pattern — Invariant 2)
- All report-capable roles can reach the report via `verifyReportsAccess()`.
- Scoped by `buildChurchWhere(dbUser)` — National roles see all churches (with optional region filter), Regional Chairman sees only their region, Local Pastor sees only their church.
- `scopeByRole` is NOT applied — this is not a ranked list.
- The **Region filter is hidden entirely** for Regional/Local viewers (not disabled, not greyed) — enterprise-grade: don't show controls the role cannot use.

### Enterprise-grade reporting conventions (new — apply to all elements below)
- **Scope banner:** the report header carries a subtitle stating the exact scope of the caller — `"All Regions"` for National roles with no region filter, `"Region: <name>"` for Regional Chairman or for National viewers who applied a filter, `"Church: <code>"` for Local Pastor. Never let the reader assume they are seeing the whole picture if they aren't.
- **"Computed at" freshness timestamp:** the toolbar subtitle ends with `Computed: <formatDateTime(computed_at)>` — rendered from a `computed_at: string` (ISO) field returned by the server action, formatted via `formatDateTime` from `lib/utils.ts` (`Africa/Nairobi`, per Unit 17.5 rule). Refreshing the page refreshes it; no caching layer yet.
- **Explicit sorting:** every column header that carries a numeric or text value is sortable client-side — click to toggle asc/desc, default sort by `Total Gross` descending (chase list default = largest debt first). Sort state resets when the Period toggle changes.
- **Case-insensitive search:** `<TableToolbar>` search matches `church_code` (case-insensitive) OR `church_name` (case-insensitive substring). Matches the 18.2 report-table search pattern.

### Page layout (references `ui-context.md` tokens)
- **Page header:** standard `<h1>` (`text-heading-2 font-bold text-foreground`), subtitle line stating the aging basis AND the caller's scope (per § Scope banner above). Basis sentence: *"Gross outstanding aged by period due date (FIFO — oldest debt first). Approved write-offs are church-level and disclosed separately; they are not attributed to Annual or Monthly."*
- **KPI strip:** none. The footer total row IS the aggregate (matches Collections Summary's precedent — `code-standards.md` § Reporting Patterns → "no KPI strip" precedent from 18.2).
- **Toolbar (`<TableToolbar>`):** search (church code / church name), **Period toggle (Annual / Monthly)** — Base UI `<Select>` on mobile, `<Button>` group on desktop, matching the `Collections Summary` toolbar pattern — and a Region filter (`<Select>`) rendered **only** for National-level viewers. `PrintButton` and `ExportDropdown` in `filterSlot` (icon-only below `lg`, labels at `lg+`). Toolbar subtitle carries `Computed: <formatDateTime(computed_at)>`.
- **Table wrapper:** `<TableShell>` (mandatory — never inline).
- **Empty state:** centered icon, muted message "No churches with gross outstanding arrears in this scope." plus a second muted line for non-National viewers: *"If you expected data here, verify your region assignment with National HQ."*
- **Pagination:** 15 rows per page (default).

Rows with `Total Gross = 0` (fully paid, no outstanding) are excluded — this is a **chase list**, not a directory.

**Below the table** (not inside `<TableShell>`): a muted disclosure line —

> *"Approved write-offs (church-level, not attributed to Annual or Monthly): KES X across Y churches. Net Recoverable per church is in the Arrears Report."*

Rendered from `total_written_off_in_scope` and `churches_with_write_offs` returned by the server action. This line is identical in both Annual and Monthly views (the write-off amount is church-level, not ledger-attributed). This matches IFRS 9 provision-matrix disclosure style (gross aging + separate allowance/write-off disclosure) and the existing `getArrearsReport()` precedent.

### Footer total row
`<TableFooter>` inside `<TableShell>` showing sum of 0–30, 31–60, 61–90, 90+, and Total Gross across **visible, non-defunct, in-scope** rows (respects current filter/search). Defunct churches appear in the table but are **excluded from the footer total** (Invariant 8 / Unit 17 defunct handling). The write-off disclosure line (see Table structure) sits below `<TableShell>` and is **not** part of the footer total — write-offs are not ledger-attributed and must not be summed into a per-ledger footer.

### 90+ escalation
Matches `ui-context.md` § 8 — the 90+ bucket carries the amber warning pill on any row where the 90+ cell is nonzero. No percentage variant here (the dashboard chart uses 90+ > 25%; this report surfaces every church with *any* 90+ debt, which is the actionable condition).

## Implementation

### Dependencies
None. No new packages. Uses existing `<TableShell>`, `<TableToolbar>`, `<PrintButton>`, `<ExportDropdown>`, `<ExportConfirmDialog>`, `<DataTablePagination>` components and existing `lib/utils/financial.ts`, `lib/utils.ts` formatters.

### Step 1 — Extract the aging computation (behaviour-preserving, with invariant test)

`lib/actions/dashboard-actions.ts` currently computes aggregate `aging0_30`, `aging31_60`, `aging61_90`, `aging90_plus`. That logic must become reusable so the report uses **the same** aging math (Reporting Reuse Principle, `code-standards.md` § Reporting Reuse Principle). Duplicating the math is forbidden.

- **File:** `lib/utils/financial.ts` — add exported helper:
  ```ts
  export type AgingChurchInput = {
    created_at: Date
    is_defunct: boolean
    payments: Array<{
      amount_paid: number | string | { toString(): string }
      payment_type: string
      payment_date: Date
      allocations: Array<{
        amount: number | string | { toString(): string }
        allocation_type: string
      }>
    }>
    write_offs: Array<{
      amount: number | string | { toString(): string }
      status?: string
    }>
  }

  export function getAgingBuckets(
    church: AgingChurchInput,
    ledger: 'Annual' | 'Monthly' | 'Combined',
    now?: Date
  ): { bucket0_30: number; bucket31_60: number; bucket61_90: number; bucket90_plus: number };
  ```

  **Signature decisions:**
  - The `ledger` parameter is **mandatory** — the current dashboard math is combined-ledger (Annual + Monthly mixed at each cutoff). The `'Combined'` path must reproduce that exactly. The `'Annual'` and `'Monthly'` paths compute the same bucket geometry per single ledger, for the report.
  - `AgingChurchInput` is a narrow structural type — **not** the full Prisma `Church`. `dashboard-actions.ts` already selects exactly these fields (payments with `status:'Paid'` + allocations, write_offs with `status:'Approved'`). Passing the fetched shape structurally is enough; no Prisma type leaks into the helper.
  - FIFO reduction (oldest-first) is applied **only in the `'Combined'` path** to preserve today's dashboard behaviour byte-for-byte. **Per-ledger (Annual / Monthly) paths return GROSS buckets — no write-off reduction** — because `WriteOff` has no ledger attribution and prorating would invent data the schema does not hold. This matches IFRS 9 provision-matrix disclosure (gross aging + separate allowance line) and the existing `getArrearsReport()` convention. Per-ledger write-off netting is explicitly deferred until a future unit adds ledger attribution to `WriteOff`.

- **File:** `lib/actions/dashboard-actions.ts` — replace inline aging computation with a call to `getAgingBuckets(church, 'Combined', today)`. The four aggregate accumulators (`aging0_30`, etc.) are unchanged; only the source of the four per-church numbers changes. No other change.

- **Invariant test (mandatory, blocks Step 2):** Capture the current dashboard aggregate output for a known dataset *before* the refactor (either by screenshot, or by a temporary `console.log` in `dashboard-actions.ts` recording the four aggregate numbers). After the refactor, re-render the National dashboard and confirm the four aggregate numbers are **byte-identical**. Record the comparison in the session notes. If they differ for any church, the extraction is wrong — fix `getAgingBuckets` before proceeding. Do not proceed to Step 2 until this check passes. A second assertion: sum of `getAgingBuckets(church, 'Combined')` across all churches must equal the four dashboard aggregate numbers exactly.

### Step 2 — Server action

- **File:** `lib/actions/report-actions.ts` — add:
  ```ts
  export type ArrearsAgingRow = {
    church_id: string;
    church_code: string;
    church_name: string;
    region_name: string;
    is_defunct: boolean;
    annual: { bucket0_30: number; bucket31_60: number; bucket61_90: number; bucket90_plus: number; total_gross: number };
    monthly: { bucket0_30: number; bucket31_60: number; bucket61_90: number; bucket90_plus: number; total_gross: number };
  };

  export type ArrearsAgingResult = {
    rows: ArrearsAgingRow[];
    scope_label: string;                 // "All Regions" | "Region: <name>" | "Church: <code>"
    computed_at: string;                 // ISO timestamp
    total_written_off_in_scope: number;  // church-level, not ledger-attributed
    churches_with_write_offs: number;    // count of churches in scope with approved write-offs
  };

  export async function getArrearsAgingReport(
    period: 'Annual' | 'Monthly',
    regionId?: string
  ): Promise<ArrearsAgingResult>;
  ```
  - `'use server'` at top of file (already present).
  - `verifyReportsAccess()` at the top of the `try` block.
  - Scope via `buildChurchWhere(dbUser)`.
  - If `regionId` is provided AND the caller is National-level, extend the where-clause with `region_id = regionId`. Regional/Local callers ignore `regionId` (the scope helper already fails closed for them — `code-standards.md` § Region Narrowing).
  - Compute `scope_label` server-side from `dbUser.role` + applied filter (never let the client construct it).
  - Compute `computed_at` from `new Date().toISOString()`.
  - For each church in scope, call `getAgingBuckets(church, 'Annual')` and `getAgingBuckets(church, 'Monthly')`. Each row's `total_gross` = sum of the four bucket values for that ledger.
  - Filter out churches where `annual.total_gross === 0 && monthly.total_gross === 0`.
  - Compute `total_written_off_in_scope` = sum of `sumApprovedWriteOffs(church.write_offs)` across all churches in scope **with any approved write-offs** (church-level, not ledger-attributed). Compute `churches_with_write_offs` = count of churches with `write_offs.length > 0` after status filter. These fields are **identical in both Annual and Monthly views**.
  - Return `Promise<ArrearsAgingResult>`. `catch → console.error → return { rows: [], scope_label: 'Unknown', computed_at: new Date().toISOString(), total_written_off_in_scope: 0, churches_with_write_offs: 0 }` (matches 18.2 empty-array convention extended to the new shape; error-vs-empty discrimination remains tracked-deferred).
  - Read-only: no `prisma.$transaction`, no mutations, no `logAudit()`.

- **Scale Watch commitment:** this report loops all in-scope churches × 2 ledgers. At the current ~1,600 churches this is a linear walk of ~3,200 `getAgingBuckets` calls per request. Tracked in `## Scale Watch` under the existing "Report p95 response time" row (see § Files to modify). If p95 exceeds 3s, apply the mitigation: aggregate-query rewrite (§ Scale Watch "Compliance payload size" mitigation pattern).
