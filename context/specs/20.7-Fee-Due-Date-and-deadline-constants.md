# Unit 20.7: Fee, Due-Date & Deadline Constants

## Goal

Relocate `ANNUAL_FEE` (5000) and `MONTHLY_FEE` (500) from `lib/utils/financial.ts` to `lib/constants.ts`, and extract the inlined annual-fee March cutoff (`getMonth() <= 2`) to a named constant `ANNUAL_FEE_DUE_THROUGH_MONTH = 3`. Wire the fee strings across `lib/help/content.ts`, `components/dashboard/kpi-cards.tsx`, `components/payments/pay-now-wizard.tsx`, and `components/settings/system-config-content.tsx` — all sourced from the single-source constants — and eliminate the duplicated `ANNUAL_FEE` / `MONTHLY_FEE` consts in `lib/utils/allocation.ts` and `scripts/backfill-allocations.ts`. Zero behavioural change to the ledger engine; verified byte-identical against the 18.2.2b oracles (CH001 / CH007).

## Design

### Constant naming and placement

All three constants live in `lib/constants.ts`, matching the established single-source precedent (`FOUR_EYES_THRESHOLD`, `SLA_YELLOW_DAYS`, `PAYMENT_INTENT_AMOUNT_CEILING`). No new file, no parallel module.

**Fee constants — relocated, not renamed:**
- `ANNUAL_FEE = 5000`
- `MONTHLY_FEE = 500`

Names preserved verbatim. The existing names have consumers across `financial.ts`, `allocation.ts`, and `backfill-allocations.ts` (see amendment log). Renaming to `ANNUAL_CONTRIBUTION_FEE` / `MONTHLY_CONTRIBUTION_FEE` would touch every importer for zero behavioural value; it is the kind of "cleanup" that obscures a relocation diff. If the client later introduces additional fee types, they gain distinct names then, not now.

Value style: `5000` without a numeric separator, matching `FOUR_EYES_THRESHOLD = 20000`. `PAYMENT_INTENT_AMOUNT_CEILING = 500_000` uses a separator because six digits do; four do not need one.

**Due-date constant — new:**
- `ANNUAL_FEE_DUE_THROUGH_MONTH = 3` — 1-indexed. March.

Rule (extracted from the existing `getMonth() <= 2` comparison and its ambiguous comment):
> Churches created on or before March owe the current year's annual fee. Churches created in April or later begin owing the annual fee the **following** year.

**Why 1-indexed, not 0-indexed.** A 0-indexed constant (`ANNUAL_FEE_DUE_MONTH_MAX = 2`) preserves the exact comparison (`getMonth() <= 2`) with zero code churn at the call site. But `2` reads as "February" to every reader who has not memorised JS's month indexing, and it will confuse the person who opens this file six months from now to change the cutoff. The 1-indexed form (`= 3`, reading as "March") requires a `+ 1` at the comparison site (`getMonth() + 1 <= ANNUAL_FEE_DUE_THROUGH_MONTH`) — a one-time cost that self-documents the indexing shift. When the business asks "change the cutoff to June," the change is `3 → 6`, not `2 → 5 with a comment that 5 means June`. **Readability wins.** The comparison-site `+ 1` is the only place the shift is visible, and it is right beside the constant it shifts.

Rejected alternative: `ANNUAL_FEE_GRACE_MONTHS = 3` — inverts the boolean (`if you were created within N months of January…`) and reads as a duration. The current logic is a month-index comparison. Keep it as one.

```tsx

</Button>
<Button onClick={() => setAmount(String(ANNUAL_FEE))}>
  Pay KES {ANNUAL_FEE.toLocaleString('en-KE')}
```

Both the **label** and the **value passed to `setAmount`** must change. If only the label is templated while `setAmount('5000')` stays a literal, a future change to `ANNUAL_FEE = 6000` would render "Pay KES 6,000" while pre-filling 5,000 in the amount input — a silent four-eyes bypass candidate, because the user sees the new fee label but pays the old amount. Caught by pre-step.

`toLocaleString('en-KE')` yields `5,000` — matching the current visual register exactly. **`formatCurrency` is deliberately not used here.** It renders `KSh 5,000` (or `KES 5,000` depending on the formatter's symbol choice), changing the register from prose to a formatted number. Help copy, KPI card sublabels, and wizard button labels are narrative text — the `KES X,XXX` inline form reads as the author wrote it. `formatCurrency` is the right tool for tables and config rows (where numbers are the point); it is the wrong tool for prose-embedded numbers.

The tracker's "three strings" did not match — confirmed by pre-step as **two strings in `content.ts`, two in `kpi-cards.tsx`, two buttons (four substitutions) in `pay-now-wizard.tsx`**. Tracker corrected in Step 6.

### `components/settings/system-config-content.tsx` — Card 1 fee rows

Card 1 "Financial Controls" currently has three rows: Four-eyes threshold, Arrears critical window, Payment ceiling. The placeholder comment on the `<CardContent>` confirms 20.7's landing spot.

**Two new rows are inserted *before* the Four-eyes threshold row.** Rationale:
- Fees are the primitive amounts; four-eyes is a control threshold applied *to* those amounts. "Amounts → Controls → Windows" is a natural top-down hierarchy for a financial control card.
- The current order (Four-eyes → Arrears → Ceiling) mixes control and window with no obvious logic. Adding fees at the top restores the primitive-then-control grouping.
- The Payment ceiling row is really a *fee-related* control (an upper bound on a single church's contribution). Its position at the bottom is coincidentally correct once the fees are at the top.

```tsx
<CardContent className="space-y-6 min-w-0">
  <ConfigRow icon={Coins} label="Annual contribution fee" value={formatCurrency(ANNUAL_FEE)} />
  <ConfigRow icon={CalendarDays} label="Monthly contribution fee" value={formatCurrency(MONTHLY_FEE)} />
  <ConfigRow icon={UserCheck} label="Four-eyes threshold" value={formatCurrency(FOUR_EYES_THRESHOLD)} />
  <ConfigRow icon={Clock} label="Arrears critical window" value={`${ARREARS_CRITICAL_DAYS} days`} />
  <ConfigRow icon={Banknote} label="Payment ceiling" value={formatCurrency(PAYMENT_INTENT_AMOUNT_CEILING)} />
</CardContent>
```

Lucide icons: `Coins` for Annual, `CalendarDays` for Monthly. Both added to the existing `lucide-react` import block. `formatCurrency` is correct here (table-style row, not prose).

### Out of scope — spec-declared

- **Aging bucket cutoffs (`30`, `60`, `90`) in `getAgingBuckets`.** These are aging-report boundaries, not fee due-dates. Extracting them changes the ledger engine and requires the 18.2.2a byte-identical fixture (2,000 / 5,000 / 5,000 / 100,500) as a verification gate. Separate refactor, tracked as a **known magic-number hazard** for a future unit. Do **not** touch them in 20.7.
- **`ARREARS_CRITICAL_DAYS = 90`.** Already in `lib/constants.ts`. Do not touch.
- **A fixed monthly due-day-of-month.** No such rule exists. The monthly fee accrues per calendar month elapsed; there is no per-month day boundary. Inventing one is a product decision requiring its own spec, and violates the "do not invent product behaviour" rule.
- **Merging `ARREARS_CRITICAL_DAYS` and the aging-bucket `90`.** Same numeric value, different semantic ("critical arrears threshold" vs "90+ day aging bucket"). Do not alias one to the other.
- **`getMonth()` matches in `app/api/webhooks/kcb/route.ts:126` and `lib/actions/dashboard-actions.ts` (6 lines).** These are month-grouping utilities for the billing month and dashboard chart bucketing — **not** annual-fee cutoff logic. Do not touch.
- **`HANDOFF_UNIT_17.md:99`, `context/architecture.md:143`, `context/progress-tracker.md:272`.** Markdown prose, not UI. Do not touch.
- **Fixing the `financial.ts` comment wart on the `else` branch** — the comment `// --- 1. Annual Fee (Due after March) ---` is inaccurate but sits on a code path this unit does not modify. The extraction replaces the comparison; the comment will be **moved** to describe the new constant's semantics (the true rule), not fixed in place. Comment edits to unrelated code are not scope-creep justification.

## Pre-Step Amendment Log (from mandatory consumer enumeration)

The pre-step `git grep` sweep surfaced four additional consumer files beyond the four named in the original diagnostic. The body above has been updated in-place to reflect the amended scope; this log records the *why* so future readers can trace the expansion.

**Command substitution note:** all `findstr /S /C:"x" lib\` commands documented in the original spec draft **failed with empty output** on this environment. Bare directory paths (`lib\`) are not wildcard patterns — `findstr` searches for a *file named `lib`*, finds nothing, prints nothing, exits clean. The working replacement is **`git grep -n "<pattern>"`**, which respects `.gitignore`, prints `file:line:text` triples, and handles Windows path resolution correctly. Use `git grep` throughout this spec; ignore any residual `findstr` references in the pre-step section as historical narrative.
