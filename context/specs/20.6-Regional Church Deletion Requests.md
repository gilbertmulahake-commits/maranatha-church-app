# Unit 20.6: Regional Church Deletion Requests

## Goal

Enable Regional Chairmen and Regional Treasurers to **request** deletion of a church in their own region, with a National Operations Admin, System Admin, or National Treasurer **approving or rejecting** the request. Approval soft-deletes the church, deactivates its attached users atomically, and writes three `AuditLog` rows (`CHURCH_DELETION_REQUESTED`, `CHURCH_DELETION_APPROVED`, `CHURCH_DELETED`); a proposer cannot approve their own request (enforced server-side).

Delivered in two phases. **Phase A** (soft-delete foundation, DB only) commits and verifies before **Phase B** (workflow + approval queue, UI + guards + server actions) begins — split per `ai-workflow-rules.md` → "When to Split Work".

## Design

### Data model

**One new table.** Follows the `PendingPayment` / `UnmatchedPayment` precedent: `String` status, review-workflow field naming (`reviewed_by` / `reviewed_at`), audit via `logAudit`.

```prisma
model ChurchDeletionRequest {
  id                     String    @id @default(uuid())
  church_id              String
  church                 Church    @relation(fields: [church_id], references: [id])
  reason                 String              // "DISSOLVED" | "MERGED" | "DUPLICATE" | "OTHER"
  notes                  String?             // optional additional context
  status                 String              // "Pending" | "Approved" | "Rejected"
  proposed_by            String
  proposed_at            DateTime  @default(now())
  reviewed_by            String?
  reviewed_at            DateTime?
  rejection_reason       String?
  resulted_in_deletion   Boolean   @default(false)

  @@index([church_id])
  @@index([status])
  @@index([proposed_by])
  @@index([status, proposed_at])
}
```

Back-relation on `Church`:
```prisma
  deletion_requests     ChurchDeletionRequest[]
```

### Reason taxonomy

`reason` is a Zod-validated enum (stored as `String`, matching `WriteOff`'s pattern — no Prisma `enum`):

| Reason | Category | Notes requirement | UI treatment |
|---|---|---|---|
| `DISSOLVED` | standard | optional (`max 500`) | green "Standard" pill |
| `MERGED` | standard | optional (`max 500`) | green "Standard" pill |
| `DUPLICATE` | standard | optional (`max 500`) | green "Standard" pill |
| `OTHER` | non-standard | **required, `min 100` / `max 500`** | amber "Needs review" pill |

**Rationale.** Standard reasons correspond to laid-down procedures (a church that dissolved, merged, or duplicated a record has a known handling path). `OTHER` corresponds to cases that require out-of-app procedures — fraud, permanent relocation, leadership removal, legal intervention — and these deserve concentrated approver attention and a stronger written justification. Encoding this in the data model lets:

- The propose dialog show the correct notes requirement per reason.
- The approval queue surface `OTHER` with a distinct visual badge so the approver knows to slow down.
- The audit log record `after_data.reason_category: 'standard' | 'non_standard'` for downstream analysis.
- Future reporting ("how many non-standard deletions per region?") operate on structured data, not free-text parsing.

**Approver scope is unchanged across all four reasons** — `verifyOperationsAccess()` on both approve and reject. Escalating `OTHER` to Treasurer-only would weaken Operations Admin's authority over their own registry and is not part of this unit. If the client later wants `OTHER` to require Treasurer, that is a one-line guard change and a spec amendment — flagged in `progress-tracker.md` Open Questions at close.

**No soft-delete column on `Church` in Phase B** — Phase A adds it. The two migrations are separate.

### Phase A — Soft-delete foundation

`Church.deleted_at DateTime?` (additive, no backfill — nullable defaults `NULL`).

`deleteChurch` in `lib/actions/church-actions.ts` is rewritten to soft-delete (see Phase A implementation). This is **required** — Draft P assumed hard delete works, but `Payment.church_id` / `WriteOff.church_id` / `PendingPayment.church_id` / `PaymentIntent.church_id` are all required FKs with default `Restrict`; a hard delete fails on any realistic church. `CHURCH_DELETED` event preserved; metadata gains `soft_delete: true` and `deactivated_user_ids`.

**Two registers intentionally preserve deleted churches** (enterprise / IFRS 9:
financial disclosure registers must not hide write-offs). `getWriteOffRegister`
and `getDefunctChurchRegister` strip `deleted_at` from their church scope and
add a `church_deleted: boolean` field to their return types. Phase B renders
a `(deleted)` gray badge next to those rows per `ui-context.md` § 2 status-badge
palette (`bg-gray-100 text-gray-700 border-gray-200`). Every other church-centric
report (Arrears, Compliance, Prepayment, Inactive) excludes deleted churches
via `buildChurchWhere`. Money-ledger reports (Cashbook, Collections, YoY,
Allocation, Source/Method, Intake, Backlog, SLA) preserve via `buildPaymentWhere`
— unchanged.

**"Defunct ≠ deleted":** `is_defunct` means "written off to zero"; `deleted_at` means "removed from active views". A defunct church still appears in financial reports; a deleted one does not. Do **not** merge into one predicate.

### Phase B — Workflow + approval queue

**Propose** — new guard `verifyChurchDeletionRequestAccess(churchId)`. Regional roles only (`REGIONAL_CHAIRMAN`, `REGIONAL_TREASURER`); requires `dbUser.region_id === church.region_id`. National roles refused — they have direct delete and should not be forced through the request workflow.

**Review (approve/reject)** — reuse existing `verifyOperationsAccess()` (`OPERATIONS_ADMIN | SYSTEM_ADMIN | NATIONAL_TREASURER`). No new approval guard.

**Queue read** — `verifyOperationsAccess()`; page redirects to `/dashboard` on failure. Badge-count action returns `0` silently on auth failure so `layout.tsx` never throws.

**Four-eyes** — `proposed_by !== reviewed_by` on **both** approve **and** reject, returning `{ error }` (not throwing). Matches `approveWriteOff` / `rejectWriteOff` / `approvePendingPayment` / `rejectPendingPayment`. Unreachable by role in practice (proposer is Regional; approver is National), but present as a hard backstop.

**Atomic claim** — approve and reject both use `updateMany({ where: { id, status: 'Pending' } })` inside `$transaction`; `claimed.count === 0` throws. Prevents double-click and concurrent double-approve. Matches `approveWriteOff` precedent.

**Edge case guard** — at approval time, if the church has any `Pending` `PendingPayment`, `Pending` `WriteOff`, or `Pending` `UnmatchedPayment` assigned to it, the approval returns `{ error: 'This church has unresolved financial exceptions. Resolve them before deleting.' }` with a list of the blocking items. Prevents orphaning staged records.

### UI

**Regional entry point:** `<RequestChurchDeletionDialog>` triggered from `regional-table.tsx`'s row action menu, visible only when `userRole === 'REGIONAL'`. Fields:
- `reason` — required `<Select name="reason">`, four options per the taxonomy. Base UI nullability rule: `onValueChange` receives `string | null`; guard with `if (val)`; do not cast `as string`.
- `notes` — `<Textarea name="notes">`; required when reason = `OTHER`.

Dialog width `sm:max-w-[500px]`, cancel `variant="outline"`, submit `bg-primary` + `<Loader2>`. Submit disabled until reason selected **and** (reason ≠ `OTHER` **or** notes.trim().length ≥ 100). Helper text under Notes is **dynamic** per the Copy section. Inline validation error renders under Notes when validation fails.

**Duplicate guard UX** — before mounting the dialog, `regional-table.tsx` fetches `getPendingRequestForChurch(churchId)`. If a pending request exists, the row action is **disabled with a tooltip** ("A pending deletion request was submitted {days} days ago"). The server-side check remains as backstop.

**Cancellation** — the proposer can withdraw their own `Pending` request from the "My Deletion Requests" view via `cancelChurchDeletionRequest(requestId)`. Only `REGIONAL_CHAIRMAN`/`REGIONAL_TREASURER` who submitted it. `<AlertDialog>` confirm. Without cancellation, a mistaken submit is permanent until a National role approves or rejects.

**Regional page "My Deletion Requests" panel** — second `<Tabs>` panel below the church list, showing the current user's own submissions (all statuses). Columns: Church Code, Church Name, Status badge, Requested At, Reviewed At, Rejection Reason (if rejected), Actions (Cancel if Pending).

**National queue:** New page `/dashboard/church-deletion-requests`. Server Component under `Suspense` + `await connection()`. Renders `<ChurchDeletionRequestsTable>` with columns:

| Church | Region | Reason | Proposed By | Age (days) | Status | Actions |

- **Reason cell** renders the human label (`Dissolved` / `Merged` / `Duplicate record` / `Other`) with an adjacent badge: emerald "Standard" for the three standard reasons, amber "Needs review" for `OTHER`. The badge is **additive** — the label still renders.
- **Age column** with `<SlaBadge>` — 0–3 days green, 4–7 yellow, 8+ red (reuses `<SlaBadge>` from `components/reconciliation/sla-badge.tsx`; thresholds match `SLA_YELLOW_DAYS`/`SLA_RED_DAYS` in `lib/constants.ts`).
- **Sort default**: `[{ status: 'asc' }, { proposed_at: 'asc' }]` — Pending first, then **oldest first within status** so the riskiest item is at the top.

- **Approve dialog content**:

### Copy

- Propose dialog — Reason `<Select>`: `"Reason for deletion"` — options rendered as human-readable labels: `Dissolved` / `Merged` / `Duplicate record` / `Other (requires detailed justification)`
- Propose dialog — Notes `<Textarea>`: label `"Additional context for the approver"` · helper text below the field is **dynamic**:
  - If reason ∈ standard: `"Optional. Max 500 characters."`
  - If reason = `OTHER`: `"Required (min 100 characters). This request will be flagged for closer review."`
- Propose dialog validation: `OTHER` + notes < 100 chars → inline error `"Non-standard deletions require at least 100 characters of justification."`
- Reject dialog: `"Reason for rejection"` (required, min 5 chars, "visible to the proposer")
- Approve confirm: concrete consequence list per above (not a generic one-liner)
- Duplicate tooltip: `"A pending deletion request was submitted {days} days ago."`
- Cancellation confirm: `"Withdraw your deletion request for {church_name}? The church will remain active."`
- Edge-case error at approval: `"This church has unresolved financial exceptions. Resolve them before deleting."` followed by a list.

### Audit events

Four new `AuditLog.action` values:

- `CHURCH_DELETION_REQUESTED` — on propose. `after_data` includes `church_code`, `church_name`, `reason`, `reason_category` (`'standard' | 'non_standard'`), `notes`.
- `CHURCH_DELETION_CANCELLED` — on proposer cancellation. `after_data` includes `church_code`, `reason`.
- `CHURCH_DELETION_APPROVED` — on approve. `metadata` includes `request_id`, `church_code`, `approved_by_email`.
- `CHURCH_DELETION_REJECTED` — on reject. `after_data` includes `rejection_reason`, `request_id`; `metadata` includes `church_code`, `rejected_by_email`.

`CHURCH_DELETED` is written by the (Phase-A-rewritten) `deleteChurch()` action — fires on the approval path because approval calls it. Metadata includes `soft_delete: true`, `source: 'deletion_request'`, and `request_id`; `after_data` includes `deactivated_user_ids`.

```ts
async function softDeleteChurchTx(
  tx: Prisma.TransactionClient,
  churchId: string
): Promise<{ deactivatedUserIds: string[] }> {
  await tx.church.update({
    where: { id: churchId },
    data: { deleted_at: new Date() },
  })
  const users = await tx.user.findMany({
    where: { church_id: churchId, is_active: true },
    select: { id: true },
  })
  if (users.length > 0) {
    await tx.user.updateMany({
      where: { id: { in: users.map((u) => u.id) } },
      data: { is_active: false },
    })
  }
  return { deactivatedUserIds: users.map((u) => u.id) }
}
```

**B3. `lib/auth/guards.ts` — new guard `verifyChurchDeletionRequestAccess`**

```ts
export async function verifyChurchDeletionRequestAccess(churchId: string) {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) throw new Error('Unauthorized')

  const dbUser = await prisma.user.findUnique({ where: { id: user.id } })
  if (!dbUser) throw new Error('User not found')

  if (!isRegionalLevel(dbUser.role)) {
    throw new Error('Forbidden: Only regional roles may request church deletion')
  }

  const church = await prisma.church.findUnique({
    where: { id: churchId },
    select: { id: true, church_name: true, church_code: true, region_id: true, deleted_at: true },
  })
  if (!church) throw new Error('Church not found')
  if (church.deleted_at) throw new Error('Church is already deleted')
  if (dbUser.region_id !== church.region_id) {
    throw new Error('Forbidden: Can only request deletion for churches in your region')
  }

  return { actorId: user.id, actorEmail: user.email, actorRole: dbUser.role, dbUser, church }
}
```

Import `isRegionalLevel`.

`approveChurchDeletionRequest(id)` — the load-bearing action:

```ts
export async function approveChurchDeletionRequest(id: string) {
  try {
    const { actorId, actorEmail } = await verifyOperationsAccess()

    const request = await prisma.churchDeletionRequest.findUnique({
      where: { id },
      include: { church: { select: { church_code: true, church_name: true, deleted_at: true } } },
    })
    if (!request) return { error: 'Deletion request not found.' }
    if (request.status !== 'Pending') return { error: 'Only pending requests can be approved.' }
    if (request.proposed_by === actorId) {
      return { error: 'You cannot approve a request you proposed.' }
    }
    if (request.church.deleted_at) return { error: 'Church is already deleted.' }

    // Blocking check — do not orphan staging records
    const [pendingPayments, pendingWriteOffs, pendingUnmatched] = await Promise.all([
      prisma.pendingPayment.count({ where: { church_id: request.church_id, status: 'Pending' } }),
      prisma.writeOff.count({ where: { church_id: request.church_id, status: 'Pending' } }),
      prisma.unmatchedPayment.count({ where: { assigned_church_id: request.church_id, status: 'Pending' } }),
    ])
    if (pendingPayments + pendingWriteOffs + pendingUnmatched > 0) {
      return { error: 'This church has unresolved financial exceptions. Resolve them before deleting.' }
    }

    let deactivatedUserIds: string[] = []
    await prisma.$transaction(
      async (tx) => {
        const claimed = await tx.churchDeletionRequest.updateMany({
          where: { id, status: 'Pending' },
          data: { status: 'Approved', reviewed_by: actorId, reviewed_at: new Date(), resulted_in_deletion: true },
        })
        if (claimed.count === 0) {
          throw new Error('This request has already been processed.')
        }
        const result = await softDeleteChurchTx(tx, request.church_id)
        deactivatedUserIds = result.deactivatedUserIds
      },
      { timeout: PRISMA_TRANSACTION_TIMEOUT }
    )

    // Two audit events — deletion is a distinct lifecycle event
    await logAudit({
      action: 'CHURCH_DELETED',
      entity: 'Church',
      entityId: request.church_id,
      beforeData: {
        church_code: request.church.church_code,
        church_name: request.church.church_name,
        deleted_at: null,
      },
      afterData: { deleted_at: new Date().toISOString(), deactivated_user_ids: deactivatedUserIds },
      metadata: {
        soft_delete: true,
        source: 'deletion_request',
        request_id: id,
        church_code: request.church.church_code,
      },
    })
    await logAudit({
      action: 'CHURCH_DELETION_APPROVED',
      entity: 'ChurchDeletionRequest',
      entityId: id,
      beforeData: { status: 'Pending' },
      afterData: { status: 'Approved', resulted_in_deletion: true },
      metadata: { request_id: id, church_code: request.church.church_code, approved_by_email: actorEmail },
    })

    revalidatePath('/dashboard')
    revalidatePath('/dashboard/churches')
    revalidatePath('/dashboard/churches/[code]', 'page')
    revalidatePath('/dashboard/church-deletion-requests')
    revalidatePath('/dashboard/regions')
    revalidatePath('/dashboard/regional')
    return { success: true }
  } catch (error) {
    return { error: error instanceof Error ? error.message : 'Failed to approve deletion request.' }
  }
}
```
