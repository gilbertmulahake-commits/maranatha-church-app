# Unit 18.2-pre: Add `@@index([payment_date])` on `Payment`

## Goal
Add a single B-tree index on `Payment.payment_date` so reporting queries filter by date
range without sequential table scans. Merges as one migration + one PR before Unit 18.2
opens.

## Design
No UI. No user-facing behavior change. Only a schema-level change: one `@@index` line
on the `Payment` model and its generated migration. No data backfill, no application
code changes, no new dependency.

## Implementation

### Dependencies
- None.

### Schema change
- **`prisma/schema.prisma`** — inside the `Payment` model, add:
  ```prisma
  @@index([payment_date])
  ```
- **Migration** — run `npx prisma7 migrate dev --name add_payment_date_index`. Commit
  the generated migration folder.
- **Client regen** — `npx prisma7 generate` after migration.
- **Production deploy** — `npx prisma7 migrate deploy` on deploy (per existing migration
  workflow; no special handling).

### Files to create / modify
- `prisma/schema.prisma` — **modify** (one `@@index` line)
- `prisma/migrations/<timestamp>_add_payment_date_index/` — **create** (generated)
- `context/architecture.md` — **modify only if** a note is warranted; the growth posture
  bullet already references the index, so no additional change needed unless the index
  needs its own note

### Why this exists now
The earlier deferral rationale ("not needed for 11 churches") is stale. The system
currently holds ~1,600+ churches and grows. `Payment.payment_date` is filtered
continuously by `getDailyCashbook()`, `getCollectionsSummary()`, `getYoYComparison()`,
and any date-range report. Without the index, each such query is a sequential scan on an
ever-growing table. The index is small, cheap to maintain, and eliminates a predictable
performance cliff. It merges as a standalone prerequisite to keep Unit 18.2 read-only
and to keep the split rule (no UI+DB in one unit) intact.
