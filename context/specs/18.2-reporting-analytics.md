# Unit 18.2: Reporting Analytics & Breakdowns

## Goal
Add six read-only analytical reports — Collections Summary, Compliance, Regional Scores,
YoY Comparison, Allocation Breakdown, and Source/Method Breakdown — to the Unit 18.1
reporting hub, reusing the existing financial and scoring engines as the single source
of truth. Every report respects Strict Bucket Isolation, write-off accounting, and
role-based scope, and the closing gate passes with the page count unchanged at 28/28.

## Design

### Placement & Navigation
Six new slugs under the existing dynamic route `app/dashboard/reports/[report]/page.tsx`:
`collections-summary`, `compliance`, `regional-scores`, `yoy-comparison`,
`allocation-breakdown`, `source-method`. Because `[report]` is a **single dynamic
route**, the build page count stays **28/28** — a changed count means a route was
created outside the dynamic segment and is a defect.

The hub grid gains six cards, matching the existing pattern (no per-card role gating —
role scoping lives in the actions via `buildChurchWhere` / `buildPaymentWhere`; Regional
Scores additionally wraps its engine with a `scopeByRole` helper, see below). Local roles
(`LOCAL_PASTOR`, `CHURCH_TREASURER`) do not see Regional Scores, YoY Comparison,
Allocation Breakdown, or Source/Method Breakdown in the hub — only Compliance.

### Stage Sequencing (justified deviation from the split rule)
Both stages ship in one spec, one branch, one closing gate, because all six reports share
the guard, scope helpers, table primitives, export path, and one page-level `<Suspense>`.
The split rule in `ai-workflow-rules.md` targets mixed UI+DB / UI+background / unrelated
routes — none of which occur. Risk is managed by ordering and by verifying each stage
before starting the next.

- **Stage A (reuse existing math):** Collections Summary → Compliance → Regional Scores
- **Stage B (new aggregation):** YoY Comparison → Allocation Breakdown → Source/Method

### Layout per Report (per `ui-context.md`)
1. Page title + subtitle already come from `<ReportShell>` — do not duplicate.
2. Optional `<KpiGrid>` summary strip (`<KpiValue>` only — never inline `text-heading-*`)
   for Collections Summary, Compliance, Regional Scores.
3. `<TableToolbar>` with title, subtitle, filter `<Select>`s, and the standard icon-only
   Print/Export below `lg`. Search field only where a per-row entity exists (Compliance).
4. `<TableShell>` wrapping the table; first column is a `<Checkbox>`; financial cells
   `text-right font-medium tabular-nums`; rows `hover:bg-muted/50`.
5. `<ExportDropdown>` + `<PrintButton>` + `<ExportConfirmDialog>` — identical to 18.1.
6. Pagination: client-side 15 rows/page. The actions return **full arrays**; no server
   pagination (matches 18.1 house style — see `lib/actions/report-actions.ts`).
7. Empty state: centered icon, muted message, no CTA (read-only).

### Bucket Isolation (non-negotiable)
Annual and Monthly always occupy separate columns or separate series. No report displays
a combined "Total Collected" figure. Written-off amounts appear only as a distinct
"Less Written Off" column, never netted silently into "Collected".

### Charts
Exactly one chart in this unit: **YoY Comparison** renders a two-series (Annual / Monthly)
area or bar chart above its table, colours strictly from `globals.css` variables, no
hardcoded hex, `vertical={false}` on the grid, muted 12px axis text. Source/Method and
Allocation Breakdown are matrices — no chart. The National dashboard Tier 3 slot remains
Arrears Aging; nothing here touches it.

### Scale Considerations & Growth Assumptions (no hardcoded counts)
The system currently holds ~60 regions and ~1,600+ churches, both growing. **No report
in 18.2 may hardcode, assume, or paginate against a fixed count.** All lists, ranks, and
totals are computed from the data returned by the query, never from a literal. Where a
design choice has a growth limit, the limit and mitigation path are recorded here so
they are visible before they bite.

| Dimension | Approach | Where it will strain | Mitigation trigger |
|---|---|---|---|
| Region count | `getRegionalScores()` loops all regions dynamically — no upper bound in code | Request-cycle scoring at growth | Migrate scoring to background job when p95 request time > 2s |
| Church count (national view) | Compliance loads all in-scope churches (mirrors existing `getArrearsReport()`) | Full payment history in memory as church count grows | Adopt per-church `aggregate` query when payload > ~5,000 rows or TTFB > 3s |
| Church count (regional view) | Scoped by `buildChurchWhere` — regional viewer loads only their region | Regional counts themselves growing | Same trigger as national; existing scope helper handles isolation automatically |
| Payment row count | Grouped queries; per-church history loaded only when needed for `isChurchCompliant` | Continuous growth, unbounded | `@@index([payment_date])` required via Unit 18.2-pre before this unit opens |
| Compliance per-church load | Loads full payment history per church (mirrors existing engine) | Node memory pressure at scale | Switch to per-church `aggregate` when measured slow |
| Regional Scores (engine) | Computes all regions for every caller, then filters | Wasted work for regional viewers at growth | Cache result per request, or migrate to background at the same trigger as region count |
| Report counts displayed in UI | Always derived (`ranks.length`, `rows.length`) — no "out of 60" or "out of 1,600" literal anywhere | N/A | N/A — this is the design |

**Prerequisite to 18.2 (separate small unit, 18.2-pre):** add `@@index([payment_date])`
on `Payment` via one migration before this unit opens. The previous deferral rationale
("not needed for 11 churches") is stale at current scale. Merging the index as a
standalone pre-step keeps 18.2 read-only and keeps the split rule intact.

### Architectural findings driving this unit (recorded in `architecture.md`)
1. **Scoring engine placeholder reality.** `lib/actions/scoring-actions.ts` returns four
   score components, but `timelinessPct`, `reportingAccuracy`, and `leadershipEngagement`
   are hardcoded constants (`85`/`90`/`95` when any compliance exists, else `0`). Only
   `compliancePct` reflects real data. The 40/30/20/10 formula is real arithmetic over
   three placeholder axes. **Decision for 18.2: Option B — the report renders only the
   real components (`compliancePct`, `finalScore`, `incentiveTier`, arrears) and does
   not display the three placeholders as if they were measurements. The dashboard
   leaderboard gains a matching info tooltip on its Score column header so the two
   surfaces agree on how much of the score is instrumented. Instrumenting the three
   axes is scheduled as Unit 18.2.1 — tracked in `progress-tracker.md`.**
2. **Engine return-shape gap.** `RegionalScoreData` returns only **net** arrears
   (`outstandingAmount`, `outstandingAnnual`, `outstandingMonthly`). `code-standards.md`
   requires Gross / Less Written Off / Net Recoverable to be shown separately. **Fix
   (read-only, no behavioral change):** add `grossOutstandingAnnual`,
   `grossOutstandingMonthly`, `totalWrittenOff` to `RegionalScoreData`, populated from
   values the engine already computes internally. Existing `outstanding*` fields stay
   unchanged so the dashboard leaderboard is untouched.
3. **Engine guard observation (out of scope, flagged not fixed).** `getRegionalScores()`
   is a `'use server'` function with no `verifyReportsAccess()`. It relies on RLS at the
   DB layer for scoping. The report action wraps it (defence in depth). Adding a guard
   inside the engine would risk breaking the dashboard for a caller whose context the
   engine cannot see — so the correct fix is caller-side. Noted in `progress-tracker.md`
   as an observation; not in 18.2 scope.
4. **Compliance rule duplication risk.** The Strict Bucket Isolation compliance rule
   (`annualStatus === 'Paid' && monthlyStatus === 'Paid'`) is currently inline in
   `scoring-actions.ts`. **Fix:** extract to `lib/utils/financial.ts` as
   `isChurchCompliant(church, now): { compliant: boolean; annualStatus; monthlyStatus;
   annualPaid; monthlyPaid; expectedAnnual; expectedMonthly }` and call from both the
   engine and the new Compliance action.

### Stage A — reports that reuse existing math

**Collections Summary** — `getCollectionsSummary(period: 'month' | 'year' = 'month')`
- Group by month (or year) of `payment_date`, `status: 'Paid'` only.
- Columns: Period · Payments (count) · Annual collected · Monthly collected · Prepayment
  credit · Total received.
- Prepayment credit = sum of `PaymentAllocation.amount` where `allocation_type` matches
  the bucket AND `billing_year > currentYear`. Derived per period by summing allocations
  linked to that period's payments.
- Scope: `buildPaymentWhere(dbUser)`; region filter for national roles via toolbar.
- Defunct churches **included** (financial report); subtitle carries a "includes defunct"
  note.

**Compliance** — `getComplianceReport()`
- Per-church row using `isChurchCompliant(church, now)` — never re-derives the rule.
- Columns: Church code · Name · Region · Annual status · Monthly status · Annual
  paid/expected · Monthly paid/expected · Gross outstanding · Less written off · Net
  recoverable · Status badge · `Defunct` badge where `is_defunct`.
- Defunct churches: **excluded from the summary-strip denominator**; **included in the
  table body below a visual separator** with the `Defunct` badge.
- Counts **and** percentages are permitted here (the counts-only rule in
  `ui-context.md` §5.3 is scoped to the National Tier 2 dashboard card).
- Snapshot as of today. Arbitrary as-of date is out of scope.
- Filters: region, bucket status, search by code/name.

**Regional Scores** — `getRegionalScoresReport()`
- Wraps `getRegionalScores()`. Applies `scopeByRole(scores, dbUser)` after sort.
- Columns: Rank · Region · Compliance % · Score · Tier · Active Churches · Compliant
  · Gross annual · Gross monthly · Less written off · Net recoverable.
- **The three placeholder components (`timelinessPct`, `reportingAccuracy`,
  `leadershipEngagement`) are NOT rendered in the table.** A subtitle states: "Score =
  40% compliance; timeliness, accuracy, and engagement axes not yet instrumented." The
  `finalScore` and `incentiveTier` still display (they are what the dashboard shows).
- Row action opens the existing `RegionBreakdownDialog` — reused, not rebuilt. Regional
  roles may open it only for their own region's row; all other rows' action is disabled.
- Sort order matches the engine exactly (finalScore descending, no added tie-break).
- **Rationale for request-cycle scoring:** matching the existing dashboard leaderboard.
  The region count grows; the computation loops all regions and all their churches on
  every call, including for regional viewers who will only see their own row. This is
  acceptable at present scale but is explicitly tracked — when p95 request time exceeds
  2s, scoring moves to a background job. The exposure is documented in
  `architecture.md` under the Invariant 4 note, not hidden, and not newly introduced
  in 18.2.

### Stage B — reports with new aggregation

**YoY Comparison** — `getYoYComparison(regionId?: string, churchId?: string)`
- **Basis: cash received, calendar year of `payment_date`.** Stated in the subtitle.
  Prepayments count in the year cash arrived — not the year it satisfied.
- Two isolated series (Annual, Monthly), never summed.
- Years: from the earliest year with any `Payment` in scope (expected 2025) through the
  current year, descending. Years absent from data are not fabricated.
- Columns: Year · Annual collected · Monthly collected · Annual Δ · Monthly Δ ·
  Annual % · Monthly %. Prior year zero → Δ and % render `—` (never `0%` / `Infinity` /
  `NaN`).
- Filters: region, church. Chart above the table: two-series area/bar, CSS-variable
  colours only, `vertical={false}` grid.

**Allocation Breakdown** — `getAllocationBreakdown(periodStart: Date, periodEnd: Date)`
- Aggregated by `billing_year × allocation_type` over the selected period (default:
  current calendar year).
- Columns: Billing year · Bucket · Allocated · Allocations count · Payments in scope ·
  Total received in scope · **Discrepancy**.
- **Reconciliation column is mandatory.** `Σ PaymentAllocation.amount` for the scope must
  equal `Σ Payment.amount` for the same scope. Any nonzero row renders the amount in
  `text-destructive` with a warning badge.
- Aggregate view only. The per-payment Allocation Breakdown modal from Unit 14.5 is
  unchanged and remains the drill-down.
- Scope: `buildPaymentWhere(dbUser)`; region filter for national roles.

**Source/Method Breakdown** — `getSourceMethodBreakdown(regionId?, dateFrom?, dateTo?)`
- Cross-tab: rows = `Payment.source` (`Webhook` / `Manual` / `Resolved`), columns =
  `PaymentMethod` (`M_Pesa` / `Cash` / `Bank_Transfer` / `Cheque`). Method labels via
  `getReadableMethod()` — imported, not duplicated.
- Cells: amount. Footer row and column totals.
- **Explicitly excluded:** `PendingPayment` rows (not ledger entries), `UnmatchedPayment`
  rows (owned by Unit 18.3), all write-offs (not payments).
- Scope: `buildPaymentWhere(dbUser)`; region filter for national roles.
